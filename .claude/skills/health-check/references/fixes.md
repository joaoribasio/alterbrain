# Fixes for each health check

Use this table after `node system/scripts/doctor.mjs --json`. Match on the check name or its plain-language meaning, because the exact check ids may differ slightly. Always ask before running a fix.

Commands are written for the terminal Claude Code already uses. On Windows use `winget`. On macOS use `brew`.

## Required checks

| Check | What to tell the user | Fix |
|---|---|---|
| **Node.js 20 or newer** | Node is the engine that runs Alterbrain's small helper programs. Yours is missing or too old. | Windows: `winget install OpenJS.NodeJS.LTS`. macOS: `brew install node`. Then ask the user to restart Claude Code. |
| **git** | Git keeps a safe history of your files. It is not installed. | Windows: `winget install Git.Git`. macOS: `xcode-select --install` or `brew install git`. Restart Claude Code afterwards. |
| **git-lfs** | Git LFS stores only big files, those of 50 MB or more (the limit is `git.lfs_min_mb` in `config/brain.json`). Notes, PDFs and slides are saved as normal files. Without it, a file that big is left out of the backup and a task says so. | Windows: `winget install GitHub.GitLFS`. macOS: `brew install git-lfs`. Then run `git lfs install`. Low urgency unless the user has files that big. |
| **GitHub sign-in (gh)** | Alterbrain backs up your work to a private GitHub repository. You are not signed in. | The user runs `gh auth login` in their own terminal and follows the prompts. Do not run it for them. If `gh` is missing: Windows `winget install GitHub.cli`, macOS `brew install gh`. |
| **Backup repository (origin)** | Your work is not yet backed up online. | Run `node system/scripts/setup-github.mjs --name <repo-name>` (it creates a private repository). Ask the user for the repo name, suggest `alterbrain-<their first name>`. |
| **Half-finished save or join** (`git-in-progress`) | A join of your work with the online copy (a rebase or a merge) was started and never finished. Until it is cleared, automatic saves refuse to run, so new work is not being saved. Your files are safe. | Ask first. Then run `git rebase --abort` if the check says rebase, or `git merge --abort` if it says merge. This puts things back as they were before the join started; it does not delete your work. Never use `reset --hard`. Then run `node system/scripts/git-auto.mjs status` and the health check again. If the abort fails, stop, add a `#ab/git` task and explain in one sentence. |
| **Model is sonnet** | Alterbrain works best on the Sonnet model. It saves your allowance. | Tell the user to type `/model sonnet` in Claude Code. Do not edit `.claude/settings.json`. |
| **Claude Code version** | Your Claude Code is older than the minimum Alterbrain needs (see `min_claude_code` in `system/release.json`). | Tell the user to update Claude Code with the method they installed it with (the desktop app updates itself; the terminal version uses `claude update`). Ask them to restart afterwards. |
| **Onboarding finished** | Alterbrain has not finished getting to know you. | Offer to run `/onboard`. |
| **Vault folders** | Some folders in `vault/` are missing. | With approval, create only the missing empty folders listed in SPEC section 3. Never overwrite a file. If `Home.md` or `Tasks.md` is missing, copy it from `system/templates/` only if the template exists; otherwise offer `/onboard`. |
| **Framework files unchanged** | A protected framework file differs from the released version. It may have been edited by hand or damaged. | Do not edit it. Offer `/update-alterbrain`, which restores released files safely. In dev mode, ignore this check. |
| **Skills and agents valid** (`validate.mjs`) | One of the skill or agent files has a formatting mistake. | Run `node system/scripts/validate.mjs` and read the message. If the file is the user's own (`my-` prefix), offer to fix the header. If it is a framework file, offer `/update-alterbrain`. |
| **Tool connections file (`.mcp.json`)** | The file that lists connected tools is missing or broken. | Run `node system/scripts/mcp-gen.mjs --dry-run` first and show the result. With approval, run `node system/scripts/mcp-gen.mjs`. |
| **Disk space** | Your disk is nearly full. | Explain that big files can stay on this machine only (`vault/40_sources/raw/_local/`). Offer to list the five largest files in `vault/40_sources/raw/` (read-only). Never delete anything. |
| **Backup size** (`repo-size`) | The history that is saved and uploaded has grown big. At 1 GB the doctor only prints a tip. At 4 GB it warns, because saving and joining get slower and GitHub recommends keeping repositories small. Big files stored with Git LFS are not counted. | Explain that deleting a file does not shrink the history, because the old versions stay in it. New big files that do not need a backup go in `vault/40_sources/raw/_local/` (this computer only). If the user wants the history made smaller, say that the only clean ways are to start a fresh private repository or to rewrite history; both are their decision, and you must not rewrite history yourself. |
| **Big files left out of the backup** (a task tagged `#ab/git`, not a doctor check) | A file was too big or could not be stored safely, so the save left it out. The file is still on this computer. The task says which of these it is. | **Git LFS is not installed:** offer the Git LFS fix above, then the next save stores the files. **A very large private file** (the task names no file): the file sits in an encrypted folder, where Git LFS cannot be used. It stays on this computer only. Suggest moving it to a folder that is not encrypted, or keeping their own copy elsewhere. **2 GB or more:** too big to back up safely; suggest a smaller version or their own copy elsewhere. **Outside the vault:** ask them to move it into the vault. **Could not set up storage:** look at `vault/.gitattributes` and at other `.gitattributes` files in the same folders (a deeper one wins over it); ask before changing anything. Tick the task once the file is saved. |
| **Big-file check for Obsidian Git** (`big-file-hook`) | Obsidian Git saves your notes by itself every 10 minutes and does not go through Alterbrain's own save. A small check that Git runs before every save sends big files (50 MB or more) to Git LFS first. That check is not in place, so a very large file saved by Obsidian Git could stop your online backup. | Run `node system/scripts/git-auto.mjs hook` (safe to repeat; the automatic save installs it too). If it says another tool already has a check (the file `.git/hooks/pre-commit`) or that Git uses a shared hooks folder, do not touch that: say so plainly, and suggest keeping big files out of the vault (`vault/40_sources/raw/_local/` stays on this computer) or switching Obsidian Git off until the user decides. A phone's Git never runs this check, so the next row can still happen. |
| **Files too big to upload** (`big-blobs`, or a task "A very big file was saved as an ordinary file") | A file of about 100 MB or more was saved as an ordinary file, usually by Obsidian Git on a phone or on a computer without the check above. GitHub refuses files that big, so the online backup is paused. Nothing is lost and nothing was uploaded: everything is safe on this computer. | The doctor only counts saves that are not online yet. With the user's OK, in these steps: (1) tell them in plain words: "I will fold the saves that are not online yet into one new save, so the big file goes through Git LFS. No file changes and nothing online is touched." (2) Run `git reset --soft "@{u}"` (with the quotes, so PowerShell accepts it; it moves no file; the changes stay waiting to be saved), then `node system/scripts/git-auto.mjs commit`, then `node system/scripts/git-auto.mjs push`, then the doctor again. This is the one change to saved history that is allowed, because these saves exist only on this computer. Never do it for anything that is already online, and never use `git lfs migrate`, `filter-repo` or a force-push. (3) If `"@{u}"` does not resolve (the branch was never uploaded), or the big file is also in a save that is already online, stop and tell the user plainly: the clean fix is then a fresh private repository, which is their decision. Tick the task once the push works. |
| **A big upload is running in the background** (`git-auto.mjs status` says so; `state/local/git.log` has `background-upload` lines) | A big file is being uploaded by a separate process, so that the end of a Claude session does not cut it short (Git LFS cannot resume a stopped upload). Notes written meanwhile are saved on this computer and go online when it finishes. | Nothing to do. If it has run for hours with no change, read the last `background-upload` lines in `state/local/git.log`. A leftover `state/local/lfs-upload.lock` from a computer that was switched off is ignored by itself once its process is gone or after 3 hours; never delete the lock while the process is alive. |

## Routines (scheduled jobs)

One doctor line (`routines`). `routines.mjs list`, `overdue` and `show` exit with 1 when something needs attention; that is a finding, not a crash, so read the output. They list active routines that are overdue, routine notes with wrong values (invalid) and notes that cannot be read as a routine at all (unreadable: no top block, a block that is not closed, or no `type` line). No `vault/90_routines/` folder means no routines: nothing to check. Alterbrain runs no scheduler of its own; the job runs from the Claude desktop app, a Claude cloud routine or a server, and the routine note only records it.

| Check | What to tell the user | Fix |
|---|---|---|
| **Overdue routine** | "<Name> has not run since <weekday date>." The usual causes: the laptop was asleep or the Claude app closed at the due time (the app does one catch-up run when it reopens), the schedule was deleted or paused on the host, the run stopped on a permission prompt, or the job ran but did not record itself. | Show `node system/scripts/routines.mjs show "<Name>"`. Offer, one at a time: (1) open the Claude app's Routines page and press "Run now" once, approving what it asks (recommended: proves the schedule works); (2) recreate the schedule from the note body, which is the exact instruction (paste it into the host); (3) pause the routine: set `status: "paused"` in the note, after the user says yes. A job that ran but did not record: record it with `node system/scripts/routines.mjs record "<Name>" --result "<one line>"` only if the user confirms it ran. Never mark a run that did not happen. |
| **Unreadable routine note** | The doctor says "cannot be read" and names the note and why: the top block (between two `---` lines) is missing or not closed, or there is no `type: "routine"` line. Until it is repaired the job is not checked, so it cannot be flagged late. | Show the first lines of the note and the missing piece; with approval repair only that top block (the template is `system/templates/notes/routine.md`), or, if the file is not a routine, offer to move it out of `vault/90_routines/`. Then run `node system/scripts/routines.mjs show "<Name>"` to confirm. |
| **Invalid routine note** | The note cannot be used as written; the doctor names the field. Most often `may` is not "draft only" (the only allowed value: the body tells a scheduled job to draft only, but `config/autonomy.json` decides what a run can really send), or `cadence` is not in the form `daily@HH:MM`, `weekly:mon@HH:MM` or `monthly:1@HH:MM`. | Show the line and the allowed form; with approval edit that one frontmatter line in the note. For `may`, set it back to "draft only" and say why. Then run `node system/scripts/routines.mjs show "<Name>"` to confirm. |

## Optional checks

| Check | What to tell the user | Fix |
|---|---|---|
| **Quarto** | Quarto turns your notes into polished PDFs. You only need it for `/render` and assignments. | Windows: `winget install Posit.Quarto`. macOS: `brew install --cask quarto`. |
| **Obsidian settings** | Obsidian has not been set up with Alterbrain's recommended settings. | With approval, run `node system/scripts/obsidian-setup.mjs`. It downloads a few pinned plugins and checks them, and also switches on "Detect all file extensions" so Word, PowerPoint and Excel files show in the file list. Tell the user it needs internet, and that they must **close and reopen the vault once** (Obsidian reads its settings when a vault opens). Offer it to anyone who set Obsidian up before this setting existed and cannot see their .docx, .pptx or .xlsx files. |
| **PDF page renderer** (`pdf-pages`; a tip, never a failure) | A small free tool (Poppler) that turns the pages of a PDF into pictures. Without it I cannot look at the pages of a report or deck I made, so I cannot check the layout by eye. Offer it **once**, at the end of a health check or during setup, never in the middle of a piece of work. If the user says no, do not offer it again unless they ask. | Ask first: "Install Poppler (about 30 MB)? It only adds the tool; nothing else changes." Windows: `winget install --id oschwartz10612.Poppler -e` (the package id is in the Windows package list microsoft/winget-pkgs, versions 24.08.0 and 25.07.0; the package puts `pdftoppm` in the WinGet links folder). macOS: `brew install poppler` ([Source: formulae.brew.sh/formula/poppler | 2026-10-08 | confidence: medium]). Then **close and reopen Claude** so the new tool is found, and run the health check again. |

## Encryption of private notes (only shown when the user turned it on)

Guide for the user: `system/docs/guides/encrypting-private-notes.md`. Never open, print or copy a key file, and never ask for its password in chat. Passwords are typed by the user in a terminal (the Terminal panel in the desktop app).

| Check | What to tell the user | Fix |
|---|---|---|
| **Encryption tool (git-crypt)** | The small free tool that scrambles your private notes is missing, so changes to them are not being saved. | Windows: `winget install --id AGWA.git-crypt -e`. macOS: `brew install git-crypt`. Ask first. Then close and reopen the Claude app. |
| **Private notes unlocked** | This computer has no key, so private notes are unreadable here and changes to them are not saved. | The user runs `node system/scripts/vault-key.mjs unlock --key "<their key file>"` (in their terminal if the key copy has a password). If they have no key file, say plainly that nothing can unlock these notes without it. |
| **Private notes encrypted online** (fail) | A saved private note is stored as plain text, or the settings that choose the encrypted notes are incomplete. Nothing is uploaded while this is the case. | With approval, run `node system/scripts/vault-key.mjs setup` (safe to repeat; it saves the notes again, encrypted). If a plain version was uploaded earlier (before encryption was on, or by another tool), say that old versions stay readable online, and that a fresh private repository is the only clean fix and is the user's decision. Never rewrite history. |
| **Upload check for private notes** (`encryption-push-hook`) | A small check that Git runs before every upload is not in place, so Obsidian Git (or another Git tool) could upload a private note without encryption from a computer that cannot encrypt it. | With approval, run `node system/scripts/vault-key.mjs setup` (safe to repeat; it installs the check). If another tool already uses that spot, or Git is set to use a shared hooks folder, do not touch it: say so plainly and suggest keeping Obsidian Git switched off. |
| **Vault key backup tested** | The backup copy of your key file has never been tested. If you lose this laptop, an untested copy may not save your notes. | Help them make a copy if they have none (`vault-key.mjs export --out "<a folder outside the project>"`, with `--password` typed by them in a terminal), then the test: `vault-key.mjs check --key "<file>"`. |

## After a fix

- Re-run the doctor.
- If a fix needs a restart (Node, git, Claude Code), say so plainly and stop there. Do not try to continue in the old session.
- If a fix fails twice, stop, explain in one sentence, add a task with `--tag health-check`, and move on to the next problem.
