# 0019. Optional encryption at rest for the most private notes

Status: accepted (2026-10-07, framework owner). Amended the same day: the scope now includes documents and pictures (made possible by [ADR 0020](0020-git-lfs-for-large-files-only.md)), an upload check closes the Obsidian Git gap on a computer, and the Windows behaviour of git-crypt 0.7.0 was run instead of assumed.

## Context
ADR 0018 made Alterbrain a store-freely brain: the vault may hold special-category facts about the user (health, nationality, family, finances), and the only protection for the copy on GitHub is the user's GitHub account. That ADR rejected encrypting sensitive facts at rest because it assumed key management that a non-technical user could not handle, and because Claude must read the facts in the clear. The second point still holds for the working copy. The first point no longer needs to decide the question for the copy that leaves the computer, because there is a tool that encrypts only on the way to GitHub and decrypts on the way back, with one key file and no daily typing.

The risk this addresses is narrow and real: a leak of the user's GitHub account or private repository would expose the facts, voice samples, people notes and journal that the brain now holds. It does not address Anthropic processing the notes in a session (ADR 0018, point 5), a stolen unlocked laptop, or anything that has already been uploaded.

## Decision
Offer, as an optional step in onboarding (after the private repository exists, before personal data is written) and later in `/reconfigure`, encryption of the most private notes in the GitHub copy with **git-crypt**, using the key-file mode (no GPG).

1. **Scope.** Two kinds of file, in these folders only: notes (`*.md *.json *.txt *.csv *.yml *.yaml *.base *.canvas`) and documents and pictures (`*.pdf *.docx *.doc *.xlsx *.xls *.pptx *.ppt *.png *.jpg *.jpeg *.gif *.webp *.heic *.rtf *.odt`). The folders are `vault/80_me/` (`fact-sheet.md`, `USER.md`, `MEMORY.md`, `voice/**`, `private/**`; not `SOUL.md`, `IDENTITY.md` or `brand/**`), `vault/60_people/` and `vault/70_journal/`. The rules are per-folder `.gitattributes` files written by `vault-key.mjs setup`, never the root `.gitattributes`, because `/update-alterbrain` replaces root framework files verbatim and `vault/` is outside the update's reach. Document rules also carry `-text`, so Git never changes line endings inside them. A rule in one of these folders is deeper than any rule in the root file, so it wins for the filter. The first version of this ADR left documents out because every binary then went through Git LFS, and one file cannot use both LFS and git-crypt. ADR 0020 ended that: ordinary documents are normal files, so they can be encrypted. One case remains. A private file of 50 MB or more would have to use Git LFS, so it cannot also be encrypted; it is left out of the online backup, with one task that names no file. Audio, video and zip files are not encrypted anywhere.
2. **Files stay plain on the laptop.** Claude and Obsidian read them normally. The key lives in `.git/git-crypt/keys/default`. The recorded setting is `config/brain.json` `privacy.encryption` `{enabled, tool, scope, key_backup_checked}`: paths and a date, never key material.
3. **The password belongs to the backup copy, not to git-crypt.** git-crypt has no password. `vault-key.mjs export` can wrap the exported key file with a password the user chooses (scrypt N=2^17 r=8 p=1, then AES-256-GCM with a random IV, fixed extra data `alterbrain-vault-key-v1`, JSON output). The wrap uses Node's built-in `crypto`. The password is read only from a real keyboard (hidden input) and never from an argument, an environment variable or a pipe, so Claude cannot see it. A key copy inside the project is refused by the script and by `block_secrets`; `*.abkey` and `vault-key-*.key` are in `.gitignore`.
4. **The key-loss warning is part of the decision.** It appears before the user agrees and again when the key is exported. Losing the key file (and its password, if set) together with the laptop makes the encrypted notes unrecoverable by anyone. Forgetting only the password while the laptop works is recoverable by exporting a new copy. The recovery drill (`vault-key.mjs check`) proves a copy opens and matches, records the date, and the session digest and the health check nag until it has been done once.
5. **The automatic save is made safe for it.** In `git-auto.mjs`: a copy that cannot encrypt (locked, or git-crypt missing) does not stage encrypted paths (git stores plain text silently when the filter is not configured), commits the rest and adds one deduplicated task; a private note that would be stored as plain text is taken out of the save; and before any push, every commit about to go up is checked by reading the stored bytes for the git-crypt header. If a plain private note is found the push is refused and a high-priority task says why. **This push check fails closed**: if it cannot run, nothing is pushed. That is the one deliberate exception to the rule that hooks and the automatic save fail open (SPEC §14), because an upload cannot be taken back. It never forces and never rewrites history.
   - **The same check runs inside Git, for every tool on a computer.** Obsidian Git uploads on its own and never goes through `git-auto`, so `system/scripts/git-hooks/pre-push.mjs` is run by a small `pre-push` hook in `.git/hooks/` (installed or refreshed by `vault-key.mjs setup` and `unlock`, and quietly at the start of each session). It reads the lines Git gives it, audits the commits the upload would send, and refuses (exit 1, one plain line starting "Alterbrain stopped this upload", one high-priority task) if any of them holds a private file without the git-crypt header. It fails closed, like the push check above.
   - **It audits only what this computer would add.** A merge commit is read with a combined diff, which lists only files that differ from every parent, so notes that another device already put online do not stop an upload after Obsidian Git joins them in. Stored files are read in bounded memory: in groups of at most 64 MiB, and a file over 8 MiB by its first bytes only, so an upload of many large scans stays quick.
   - **It keeps Git LFS working.** Git LFS writes its own upload step into the same hook file, so ours runs that step afterwards with the same input and exit code. Like the standard LFS hook, it refuses the upload (exit 2) when a folder uses Git LFS (a non-comment `filter=lfs` attribute line, or LFS in the folder's own Git settings) and `git-lfs` cannot be found, because the big files would reach GitHub as empty placeholders.
   - **It never replaces another tool's hook.** Only a hook that is empty, absent, ours or the standard Git LFS text is written over. Any other hook, and any `core.hooksPath` setting, is left alone and reported (`push-hook-foreign`, `push-hook-shared-folder`).
   - **It cannot cover a phone.** Git on a phone runs no hooks.
6. **Honest limits are written down.** File names, sizes and timing stay visible; notes saved before encryption stay readable in the old history (the only clean fix is a fresh private repository, the user's decision); files outside the three folders are not covered; a private file of 50 MB or more cannot be encrypted and is kept off the online backup; cloud sessions and always-on servers cannot read encrypted notes without the key; Obsidian on phones cannot read them and its Git plugin there would not encrypt or run the upload check; two computers editing one encrypted note give an unmergeable conflict.

## Consequences
- A leak of the GitHub account no longer exposes the facts, people and journal that were saved after the user turned this on. The user takes on one new duty: keep the key file safe and test it. The cost of failure is permanent loss of those notes if both the key file and the laptop go.
- New computers need two steps (install git-crypt, unlock with the key file). The digest and tasks say how.
- `USER.md` and `MEMORY.md` are imported into every session through `CLAUDE.md`. A session that does not hold the key (a cloud session, an always-on server) reads scrambled bytes for those two files. The guide says so; the framework does not try to hide it.
- One more tool to keep working. git-crypt is not bundled or downloaded by Alterbrain: the user installs it with `winget install --id AGWA.git-crypt -e` or `brew install git-crypt`, after Claude asks. git-crypt 0.7.0 was run on Windows 11 while building this: winget puts it in `%LOCALAPPDATA%\Microsoft\WinGet\Packages\AGWA.git-crypt_<source>\git-crypt.exe` and makes no shim in the `Links` folder; `--version` prints on standard output and exits 0; `init` writes the filter settings with absolute paths; `export-key` writes a 148-byte file; a fresh clone shows `\0GITCRYPT\0` ciphertext; `unlock` restores plain text; and a clone that has not been unlocked commits a new private file as plain text, with no error. That last behaviour is why the save and the upload check read the stored bytes themselves. A program that was open during the install (such as the Claude desktop app) does not see the new search path until it restarts, so `resolveGitCrypt` also looks in the winget folders (every `AGWA.git-crypt_*`, found by listing the packages folder), and no restart is needed. The search order is `ALTERBRAIN_GIT_CRYPT`, then the search path, then `WinGet\Links`, then the winget package folders, then the Homebrew paths on a Mac. Only Windows 11 was run; macOS and Linux were not. Tests use a stand-in that mimics the observable behaviour, and the tests that need the real binary use the one found by the resolver and skip when there is none.
- Obsidian Git (installed by `obsidian-setup.mjs`) commits and uploads every 10 minutes by itself, outside `git-auto`. With the working filter in place it encrypts through the git command line. On a locked computer it could save a new private note as plain text; the upload check in point 5 now refuses that upload on a computer, so the plain note stays local. A phone is not covered: its Git runs no hooks, so the guide tells the user not to use Obsidian Git on a phone with an encrypted vault. The hook cannot be installed when another tool owns `.git/hooks/pre-push` or Git uses a shared hooks folder; `status` and the health check say so, and the user keeps Obsidian Git off on that computer. A private file of 50 MB or more is handled by the `pre-commit` check from ADR 0020: it is taken out of the save, on a computer, whichever Git tool made it. (Its folder rule is deeper than any rule in `vault/.gitattributes`, so git-crypt would otherwise win.) The `pre-push` hook itself does not look at file sizes.
- Enforcement is in code where it can be (`vault-key.mjs`, `git-auto.mjs`, `block_secrets`, `doctor`), and tested with synthetic fixtures.

## Alternatives considered
- **Obsidian Sync (end-to-end encrypted).** A paid service that replaces the GitHub backup for the vault, and does not cover Claude's own view of the files. It changes the product's backup model and cost. Rejected for the default path; compatible with it for users who want it.
- **Keep private notes local only, with an encrypted backup elsewhere.** Strongest against a GitHub leak. It also splits the vault in two (what syncs and what does not), breaks the single-backup promise of ADR 0004, and makes cloud sessions and a second computer fail silently. Rejected.
- **A custom Node git filter.** Zero dependencies and no extra tool, but home-made cryptography in the commit path of every save. A bug there corrupts or leaks the user's notes without anyone noticing. Rejected: we wrap a small key file with Node's built-in primitives, which is a one-shot step with a read-back check, not a filter that runs on every save.
- **git-crypt in GPG mode.** Per-user keys and easy revocation. It needs GnuPG installed, configured and understood, which is too heavy on Windows for a non-technical user. Rejected in favour of the symmetric key file.
- **Encrypt everything, not only the private folders.** Breaks wiki links in the GitHub view, Git LFS for files of 50 MB or more, and every cloud-session read of ordinary notes, for little extra protection. Rejected.
- **Leave documents and pictures unencrypted (the first version of this ADR).** It was forced by Git LFS, which one file cannot share with git-crypt. With LFS limited to files of 50 MB or more (ADR 0020), the reason is gone, and a private PDF or scan is as sensitive as a private note. Superseded.
- **Guard Obsidian Git by switching its automatic save off.** Removes a backup the user may rely on, and does nothing for an upload started by hand or by another tool. Rejected in favour of the `pre-push` hook, which covers every Git tool on a computer.
