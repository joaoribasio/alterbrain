# 0020. Git LFS only for large files

Status: accepted (2026-10-07, framework owner). Supersedes the Git LFS part of [ADR 0007](0007-vault-layout-raw-first-lfs.md).

## Context
ADR 0007 sent every binary document in the vault (PDF, Word, Excel, PowerPoint, pictures, audio, video, zip, mbox) through Git LFS, using extension rules in the root `.gitattributes`. Git LFS keeps a small placeholder (a pointer) in the repository and the file itself in separate storage on GitHub. For a student's vault, where most documents are a few megabytes, that choice cost more than it saved:

- **An extra install step.** Every user needed Git LFS before the online backup could work, and `setup-github.mjs` refused to run without it.
- **An allowance to run out of.** GitHub gives each account a limited amount of LFS storage and monthly downloads. A vault full of readings and slides can use it up, and then the backup stops. [Unverified: GitHub's current figures were not checked.]
- **Phones.** LFS files did not work with Obsidian Git on a phone. [Unverified: taken from the product owner's brief, not tested here.]
- **No encryption for private documents.** One file cannot use both Git LFS and git-crypt, so ADR 0019 had to leave private PDFs and pictures unencrypted.
- **Extension rules are blunt.** A 200 KB PDF and a 400 MB recording took the same path, and Git attributes can only match file names, never file sizes.

The thing LFS is genuinely needed for is the rare very large file: GitHub refuses ordinary files of about 100 MB, and one such file saved by accident blocks every later upload until history is rewritten. [Unverified: the exact figure is from memory.]

## Decision
Ordinary documents are ordinary Git files. Git LFS is used only for files at or above a size limit.

1. **The limit is 50 MB**, set in `config/brain.json` as `git.lfs_min_mb` (default 50 when the key is absent; accepted range 1 to 95; 1 MB is 1,048,576 bytes). The product owner chose 50 MB over the 20 MB first proposed. [Inference] A 20 MB limit would send some scanned readings and image-heavy slide decks to LFS, which brings back part of the cost above for little gain.
2. **No LFS rules in the root `.gitattributes`.** An update replaces that file verbatim, and a rule per file cannot live in a file that is replaced. The root file keeps line-ending rules and marks common document, picture, audio, video and archive types `binary`, so Git never changes their bytes.
3. **Exact-path rules in `vault/.gitattributes`.** Git attributes cannot test a size, so a program does it. Before staging, the automatic save (`commitAll` in `system/lib/git.mjs`, used by `git-auto`, the save before a join, the first upload in `setup-github.mjs` and the save before an unlock) finds each new or changed file at or above the limit and adds one line for that path (`/40_sources/raw/2026/talk.mov filter=lfs diff=lfs merge=lfs -text`; anchored with a leading slash, wildcard characters escaped, names with spaces quoted). `vault/` is a user folder, so an update never touches that file. The root file marks `vault/.gitattributes` `merge=union`, so two computers that each add rules join cleanly.
4. **Existing LFS files stay in LFS.** Nothing is migrated and no history is rewritten. Files that are stored as LFS pointers in the current version get an exact-path rule on the next save that has changes (self-healing), so a changed PDF is stored as a pointer again instead of as a full copy.
5. **A big file that cannot be stored safely is left out of the save, with a task.** Reasons: Git LFS is not installed; the file sits in an encrypted folder (see 7); it is 2 GB or more (`LFS_FILE_LIMIT_BYTES`, 2,000,000,000 bytes, the smaller reading of what is [Unverified] as GitHub's per-file maximum for LFS on free plans); it is outside `vault/` (no user-owned place for its rule); or the rule was written but Git does not apply it. If the check itself fails, the save is aborted, because one ordinary file of 100 MB would block every later upload.
6. **Every Git tool is covered, not only `git-auto`.** Obsidian Git saves and uploads every 10 minutes without going through `commitAll`; before this decision the root extension rules covered that path. Two layers replace them:
   - *Prevention.* `git-auto` installs a small `pre-commit` hook (`.git/hooks/pre-commit`, text in `system/lib/git.mjs`) that runs `git-auto pre-commit` before any save by any Git tool on a computer. It sends staged big files to LFS and leaves out the ones that cannot be stored, and it never stops a save, except when the big file was the only thing in it. It fails open. Someone else's `pre-commit` hook, or `core.hooksPath`, is never touched; the doctor and `git-auto status` warn instead.
   - *Detection.* A phone's Git runs no hooks. `pushCurrent` therefore scans the commits not yet online and refuses, with kind `big-blob`, when an ordinary file of 95 MiB or more is in them, before any upload starts.
7. **Uploads.** `git lfs push origin <branch>` runs before every `git push`, so a copy without LFS's own `pre-push` hook still uploads the big files first. A big upload (16 MiB or more of LFS data waiting) is started as a separate process with a lock (`state/local/lfs-upload.lock`) so the end of a Claude session does not cut it short. The SessionEnd budget is 12 s to save, 13 s to push and 4 s to hand over, inside the 30 s hook limit.
8. **Encryption.** Private documents and pictures in the encrypted folders are now ordinary files, so ADR 0019 encrypts them. A private file of 50 MB or more cannot be both encrypted and in LFS, so it is left out of the online backup, with one task that names no file.
9. **Ingest is unchanged.** `ingest.mjs` still keeps a file over 100 MB in `raw/_local/`, on this computer only. Files from 50 MB to 100 MB go to `raw/YYYY/` and, at the next save, to LFS.

## Consequences
- **The repository grows with the documents.** Ordinary files and every version of them stay in the history. `doctor.mjs` reads `git count-objects -v` (LFS files are not counted) and prints a tip from 1 GB and a warning from 4 GB. These two levels are Alterbrain's own; GitHub's recommendation on repository size is [Unverified]. Deleting a file does not shrink the history. The way to keep a new big file off the backup is `vault/40_sources/raw/_local/`.
- **Git LFS is needed only for files of 50 MB or more.** The installers still provide it (Git for Windows includes it; `install.sh` installs it with Homebrew) and `setup-github.mjs` still requires it and switches it on, so the rare big file works. Without it, such a file is left out of the backup with a task.
- **Existing users need no step.** Their LFS files stay in LFS, and the next update replaces the root file.
- **Phones are not protected from the one failure that matters.** A phone's Git can still save a big file as an ordinary file. The upload is then refused early and clearly, and the backup stays paused until the file is dealt with. The repair offered in `/health-check` folds only never-uploaded saves into one new save with `git reset --soft "@{u}"`, with the user's OK. That is a change to local history, which the SPEC says `git-auto` never makes; it is limited to saves that exist only on this computer. [Open point: the product owner should confirm this exception, or replace it with "start a fresh private repository".]
- **A big upload can outlast a Claude session.** Git LFS cannot resume a stopped upload [Unverified]. A detached process finishes it. Whether the operating system ends that process when Claude closes is [Unverified]; in tests it survived on Windows 11. If it is ended, the next save starts the upload again from the beginning of that file.
- **Notes written while a big upload runs** are saved on the computer and go online when it finishes. No partial upload of the commits before the big file is built.
- **Real GitHub was never contacted by the tests.** Uploads, restores and quota errors were run against local bare repositories only. The wording of GitHub's quota replies is [Unverified].
- **Raw sources and line endings.** `* text=auto eol=lf` still applies to text types such as `.csv`, `.txt` and `.eml` inside `raw/`, so a file saved with Windows line endings is stored with Unix ones. That conflicts with "raw sources never change". It predates this decision and is not solved here. A line `vault/40_sources/raw/** -text` in the root file would fix it.

## Alternatives considered
- **A 20 MB limit.** Fewer surprises at the 50 MB warning level, but more everyday files (scanned readings, slide decks with pictures) in LFS, and more people hitting the install step and the allowance. Rejected by the owner.
- **A 100 MB limit (GitHub's refusal level).** Leaves no margin: a file just under it is a very large ordinary file in every later clone, and the exact figure is unverified. Rejected.
- **Extension-based LFS rules in the root file (the ADR 0007 setup).** Puts every PDF in LFS, which is the cause of the cost. Rules cannot test size. And an update replaces the root file. Rejected.
- **Extension-based LFS rules in `vault/.gitattributes`.** Survives updates but is still blunt, and still blocks encrypting private documents. Rejected.
- **A migration that rewrites history to turn old LFS files back into ordinary files.** Needless risk to the user's backup for no benefit; their files work as they are. Rejected.
- **Turning Obsidian Git's automatic save off.** Simple, but removes a backup the user may rely on and does nothing for the phone. Rejected in favour of the `pre-commit` hook and the early refusal.
