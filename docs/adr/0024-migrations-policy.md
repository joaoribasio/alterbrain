# 0024. Migrations policy: a change to the shape of user data ships a migration or a documented fallback

Status: accepted (2026-10-08, product owner)

## Context
A release replaces framework files. The user's data is not framework: `config/*.json`, the notes in `vault/`, `state/*.json` and the user's own `my-*` skills and agents stay as they are. A changed template, skill, pack or catalogue entry therefore reaches new installs only. Anyone already using Alterbrain keeps the old shape until something rewrites it.

The mechanism for that rewrite existed from the start and was never used. `update.mjs finish` runs `system/scripts/migrations/*.mjs` once each, in name order, but the folder was empty, nothing in the SPEC or the rules described the contract, and the update guide said the opposite of what the mechanism does ("never touches your notes"). Release 0.2.0 changes the shape of user data in several places at once (ADR 0023): a `learner` block and `packs` in `config/brain.json`, the `school` block replaced by programme notes and a `programme` or `provider` property on courses, moved framework files that `my-*` skills may point to, and the retired Canvas connection. Without a rule, each of those would have reached existing users only if the author remembered it.

## Decision
- **The policy, binding for every release.** Any change that alters the shape of user data or config ships in the same release with (a) a migration: idempotent, safe to re-run, with plain-language output, exit 0 or 1, and tested on fixture vaults; or (b) an explicit, documented fallback. "Shape" means keys or allowed values in `config/*.json`; frontmatter keys or values in vault notes; vault folders; `state/*.json`; the ids in `config/mcp.selected.json`; and a framework path that the user's own files point to. The text lives in `.claude/rules/framework-dev.md` ("Changing user data or config (migrations)") with a short pointer in `.claude/rules/migrations.md`, which loads when a developer edits templates, skills, packs, the catalogue or `core.md`; the SPEC states it too (section 15a).
- **A documented fallback** is one SPEC sentence that names the old shape and the file that still reads it, plus a test for it.
- **Expand, then contract.** A release reads both the old and the new shape. The old shape is removed no earlier than two releases later, and by a migration, so a person who skips a release does not fall off a cliff.
- **Frozen, self-contained scripts with four-digit ids.** `system/scripts/migrations/NNNN-short-name.mjs`, ascending, never renamed, edited or deleted once released. Line 2 is `// ab-migration: <one sentence>`. A script never reads templates or other framework text that a later release may change (it embeds what it needs, such as the text of a new note), and uses `system/lib/migrate.mjs` for atomic writes. It changes structure only, never the user's prose. It touches `config/`, `vault/` (never `40_sources/raw/`) and `state/` (never `state/local/rate-guard/`), and adds tasks only through `system/lib/tasks.mjs`.
- **Report only for files the user owns.** A migration never writes `.env.local`, `.mcp.json` (except by running `mcp-gen.mjs`), `.claude/settings*.json`, `my-*` skills or agents, or framework text files. It may look and add a task. Migrations 0004 and 0005 do exactly that.
- **Nothing runs without a restore point.** `update.mjs apply-safe` makes the git tag `pre-update-<tag>` and refuses, before changing any file, when the plan has upgrades and no restore point can be made. `finish` checks for the tag again before it runs the first upgrade. A release with no upgrades does not need Git.
- **The user sees the upgrades first and reads the result after.** `update.mjs plan` returns `migrations_pending` (one sentence from each script's `ab-migration` line) and the update skill shows them under "Upgrades to your notes and settings" before the user says yes. `finish` returns `migration_notes` (what each run changed, in the script's own words). A script in the folder that the release manifest does not list, or whose checksum does not match, is not run: it is reported as skipped and makes `ok` false. A failed upgrade stops the update with its own sentence and the list of what already ran, and a retry carries on after the ones that finished.
- **Only listed scripts run.** `finish` runs a script only when the verified release manifest lists it with a matching sha256. A stray or edited script is never run.
- **The sentence is true for everyone who reads it.** The plan lists every script the install has not recorded, so an upgrade that applies to some people says so ("If you started on Alterbrain 0.1, ..."). A fresh install is not shown the upgrades it came with: they are listed in its installed manifest, the files match, and `finish` records them in `state/migrations.json` with `baseline: true` without running them. An install from an older release is never treated that way.
- **Fresh installs have no `state/migrations.json`, and every migration still does nothing on new-shape data.** `state/migrations.json` is tracked and written only by `update.mjs finish`: `{ schema: 1, applied: [{ id, at, tag, baseline? }] }`. The install does not pre-fill it. A migration meets new-shape data anyway (a person who changed things by hand, a re-run, the baseline path not applying), so each one checks the shape and prints `Nothing to do.`.
- **A test harness that finds new scripts itself.** `tests/scripts/migrations/<id>.test.mjs` per script and `all-migrations.test.mjs`, which runs every migration twice on every fixture in `tests/fixtures/migrations/` (`v0.1.0`, `v0.1.1`, `v0.2-professional`, `v0.2-online`) and checks that the 0.2 fixtures are unchanged after the first run. `validate.mjs` lints the folder: the name, a unique prefix, the `ab-migration` line within the first three lines, and a test file.
- **Release notes.** The CHANGELOG lists every migration under `### Upgrades` (naming the script) and every framework file that a release moves or removes under `### Moved` (old path, new path or "removed"). The update skill uses both lists; for the first update from 0.1, which the old `update.mjs` plans, `### Upgrades` is the only list the user sees. `node system/scripts/validate.mjs --release` makes gaps errors (and checks that every cited ADR exists and that the SPEC mentions `state/migrations.json`); `--sign-key` implies it, so nothing is signed until the notes are complete.

What release 0.2.0 does not migrate, because a fallback covers it and each is listed in the SPEC with the file that reads it: the `school` keys in `config/brain.json` and in course notes, a missing `learner` or `packs`, a missing `jobs.country`, `git.lfs_min_mb` and `privacy.encryption` absent, the class-date fields and the `Material` section absent from older course notes, the `course` key in `manifest.jsonl`, a source note that links to its course by a short link, the LFS rule that `prepareBigFiles` writes when a big file has lost it, and onboarding titles stored in `state/onboarding.json` (the code ignores them). The recipient-class ids, the lens ids, the application fields (`sponsor`, `dutch`, `salary_check`) and the `jobs.*` keys keep their names, so nothing needs to move.

## Consequences
- Every release that changes the shape of user data carries extra work: a script, a fixture, tests, two CHANGELOG lines and often a SPEC sentence. That is the price of not breaking people who already use it, and the release gate makes skipping it visible.
- A template change alone is a bug for existing users. A developer who edits a template, a skill or a pack sees the pointer rule and the question "does this alter the shape?".
- The first update from 0.1.x to 0.2.0 is planned by the old `update.mjs`, which has no `migrations_pending`. The user sees the CHANGELOG list and the new `finish` runs the scripts; from then on the preview is complete. [Unverified: this path was simulated with a local release folder, not run from an installed 0.1.x copy.]
- Git is the restore point. The automatic save before the tag skips what it cannot store (private notes it cannot encrypt, big files), so an upgrade that touched such a file would not be undone by the tag. None of the five scripts does.
- Removing a fallback is a later decision with its own migration. The earliest for the 0.2.0 fallbacks is two releases after it.

## Alternatives considered
- **Fallbacks only, no migrations.** Code reads both shapes for ever. Simple for each release, and the code collects every old shape that ever existed. Rejected as the only tool: it is the default for small changes, but it gives no way to retire an old shape or to tell the user what changed.
- **Seed `state/migrations.json` at install with every migration marked done.** A fresh install would skip them all. Rejected: if the seeded list and the shipped scripts drift apart, an unrun migration is recorded as done and never runs. The no-op rule plus a baseline derived from the installed manifest at update time cannot fall out of step with the scripts.
- **A bulk rewrite of source-note links** from short links to full paths. Hundreds of notes in the user's own vault, touched for a cosmetic gain. Rejected: the course procedure reads the short form and rewrites a link when it refreshes the Material list.
- **Let migrations edit moved framework files or `my-*` skills.** Would carry the user's edits across automatically, and would overwrite shipped changes (the grader brief and the salary table changed in the move) or the user's own work. Rejected: they report, and the update skill merges with the user's yes.
- **Run migrations without a restore point when Git is missing.** More forgiving, and an upgrade that stops half way would have nothing to go back to. Rejected: the update stops before it changes anything.
